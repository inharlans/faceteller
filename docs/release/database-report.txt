PostgresRepository is an alias in this NEW module, not the old bigint repository.
Returns list[facework.pilot_contract.Passage]. No database/socket access on import.
Each nonempty query owns/closes a connection and read-only transaction, with a
five-second statement timeout. Errors propagate as database errors rather than
being silently reported as zero matches. Empty labels return [] without connecting.

Schema and corpus contract
Schema face_release; migration 001_reference_corpus.sql is applied transactionally.
schema_migration stores filename/SHA256; changed or missing applied migrations and
out-of-order migrations fail. Migration/import/role setup share an advisory lock.
literature: literature_id TEXT primary key, title, complete original JSON document.
passage: passage_id TEXT primary key, literature_id FK, original_text, translation,
commentary, source JSONB, literature_priority, passage_order, annotation_status,
service_eligible BOOLEAN, complete original JSON document.
label: canonical feature:class TEXT key. label_passage has a composite primary key
and foreign keys, plus reverse-label lookup index. No bigint casts anywhere.
corpus_import: complete original corpus document and SHA256, one row per distinct
canonical JSON document, preserving all source/passages/extra metadata revisions.
Migration002 adds active_corpus(singleton=1,version,canonical_sha256). version is the
input schema_version rendered as text; canonical_sha256 references corpus_import.
Every successful import updates this singleton in the SAME transaction, including
re-importing an older document. Historical import times do NOT establish active
state. The reader has SELECT on this safe metadata only, with no write privileges
and still no SELECT on corpus_import or schema_migration.
ReleaseRepository.corpus_revision() returns the active hash string or None before
an explicit import. snapshot() binds revision and candidate text to one repeatable-
read, read-only transaction so concurrent imports cannot mix hashes and text.
Canonical hash is SHA256 of UTF-8 json.dumps(document,ensure_ascii=False,
sort_keys=True,separators=(',',':'),allow_nan=False); it is NOT the raw-file hash.
On an existing installation run setup_database.py provision to migrate/grant, then
re-import the intended complete corpus. Migration002 deliberately never backfills
from the most recent historical timestamp. status now includes corpus_sha256.
Local migration002 and reader grant were applied. Release DB still has no corpus,
so its active hash is correctly null; no synthetic corpus was loaded into release.
Final active-revision verification: 45 tests passed in8.192s (19 repository tests,
26 runtime tests). Actual PostgreSQL tests prove older-revision reimport changes
the active hash despite a newer historical import timestamp, concurrent import
cannot change a pinned read snapshot, no import means unknown revision, failed
imports roll back revision/text together, and reader writes/archive reads remain
denied. A separate release-reader connection confirmed safe metadata SELECT,
no corpus_import SELECT, and no active_corpus writes. No pending migrations remain.

Input is one complete JSON object with schema_version (nonempty string or integer),
sources[] and passages[]. Each source needs a nonempty string literature_id and
title. Each passage needs a unique nonempty string passage_id and literature_id
present in that input's sources, source object, required_labels array of canonical
feature:class strings, integer literature_priority and passage_order, nonempty
annotation_status, and a real boolean service_eligible. IDs are not converted to
numbers; Unicode/string keys survive unchanged. Extra input fields are preserved.
Eligible entries require nonempty original_text, translation, commentary, source
title/url/chapter/locator and at least one condition. Duplicate labels and conflicting
classes for the same feature are rejected for eligible AND rules. Excluded entries
may have empty translations/commentary/source metadata/conditions; they are stored.
Label validation checks canonical syntax, not scientific correctness or a fixed
classifier vocabulary; unsupported new-region annotations can therefore be archived.
No human review is asserted or manufactured: annotation_status is preserved verbatim.
Explicit service_eligible is honored; it does not mean independent human validation.

Import semantics
Validate the whole document before writes. In one transaction, upsert sources and
passages by their canonical IDs, replace each included passage's full mapping set,
retain all omitted source/passage records, and deactivate omitted passages for
runtime. Therefore each import must be a COMPLETE snapshot, not a partial chunk.
Importing the same input repeatedly adds no duplicate rows, mappings, or audit
entries. Reimporting an older snapshot restores its eligible projection, with its
original audit record retained. SQL failures roll back every write in that import.
Previous raw inputs remain in corpus_import; this is reference-content provenance,
not face-analysis history. No runtime result tables exist.

Candidate matching and ordering
Parameterized SQL uses text[] labels. Eligibility plus EXISTS(overlap) and
NOT EXISTS(any missing required label) enforce AND matching and exclude empty rules.
Every returned Passage contains ALL original required labels and full source dict.
Integration amendment: the response source additionally carries annotation_status
from the dedicated passage column. This column overrides a conflicting nested
source.annotation_status; raw archived JSON is unchanged. No status is converted
to human-reviewed. This closes the previous API omission of annotation provenance.
Post-amendment verification: repository suite now16 tests, combined with runtime24
tests; all40 passed in8.592s on actual local PostgreSQL plus synthetic CPU runtime.
There is no query LIMIT; the existing PassageSelector still computes per-feature
geometric-mean scores, deduplicates and applies max3 per region/max5 overall.
Repository order: literature_priority ascending, passage_order ascending, numeric
IDs numerically before nonnumeric IDs lexically, matching the selector's ID tie-break.
Numeric-looking string IDs still retain their original spelling in storage/output.
